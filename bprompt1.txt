## 6. HARDWARE AND SERIAL COMMUNICATION

The hardware interface is a core requirement, not an optional enhancement.

Inspect the actual ESP32 firmware before deciding how to communicate with it.

### Serial receiver

Implement a dedicated serial communication service that:

- Allows the operator to select an available COM port.
- Uses a configurable baud rate matching the ESP32 firmware.
- Opens and closes the serial connection safely.
- Reads incoming serial data without blocking FastAPI request handlers.
- Handles incomplete lines, malformed JSON, invalid UTF-8, timeouts, and disconnections.
- Reconnects safely when the device becomes available again.
- Avoids creating duplicate reader threads or tasks.
- Provides accurate connection status and last-received timestamp.
- Logs errors without printing cryptographic secrets.
- Shuts down cleanly.

Use a background thread, asynchronous serial library, or another justified design. Keep serial I/O isolated from API handlers.

Provide local API endpoints for:

- Listing available serial ports.
- Reading connection status.
- Connecting to a selected port.
- Disconnecting safely.
- Reading recent measurements and connection errors.

Only allow connections to appropriate serial devices. Validate user input and prevent arbitrary command execution.

### Serial protocol

Prefer newline-delimited JSON only if it is compatible with the actual firmware.

Example of a possible transport envelope:

`{"type":"evidence","payload":{...},"auth":{...}}`

This is an illustration, not the verified firmware schema.

Inspect the existing firmware and use its actual protocol. If the firmware uses another format, document it and adapt the receiver accordingly.

If a protocol change is necessary, coordinate changes between firmware and backend. Do not change the payload serialization used for HMAC verification without updating both sides and their tests.

Never treat a valid JSON message as proof of authenticity.

### Hardware scope

Implement only the sensor types and peripherals supported by the supplied hardware and firmware.

Do not fabricate readings or report a connected sensor when no sensor data has been received.

Synthetic data may be provided through an explicitly labeled development simulator for frontend development and testing. It must never be presented as real hardware evidence.

## 7. AUTHENTICATOR AND CRYPTOGRAPHIC SECURITY

This is one of the most important parts of LabGuard.

Reuse the existing authenticator instead of rewriting its cryptographic implementation unnecessarily.

The backend must invoke the actual verifier and respect the exact evidence schema, canonicalization rules, key identifiers, and authentication-tag format.

### Required verification behavior

The backend must distinguish between:

- Valid authenticated evidence.
- Invalid authentication tag.
- Unknown key identifier.
- Malformed evidence.
- Unsupported evidence schema.
- Duplicate or replayed evidence.
- Verification unavailable because of a configuration or internal error.

Do not collapse all these outcomes into a generic successful response.

### Security rules

1. Never trust a `verified: true` field supplied by the frontend or ESP32.
2. Never mark evidence valid without running cryptographic verification.
3. Use constant-time comparison through an appropriate cryptographic library.
4. Preserve the exact payload bytes or canonical serialization required by the existing implementation.
5. Do not invent or regenerate an HMAC tag during verification.
6. Do not place secret keys in React source code, API responses, logs, or Git repositories.
7. Do not silently create a replacement key when a required key is missing.
8. Keep key files outside public directories.
9. Restrict file permissions where practical on Windows.
10. Use a controlled, documented key-rotation procedure.
11. Return explicit failure results when verification cannot be performed.
12. Never expose secret key material through error messages.

The supplied ZIP may contain actual key material. Treat it as potentially exposed.

Before the final demonstration, establish a coordinated key-rotation procedure. Generate a replacement secret, update the firmware and verifier consistently, reflash the ESP32, and test valid and invalid evidence.

Do not break the existing evidence verification tests while performing this process.

### Replay protection

Inspect whether the existing evidence format supports sequence numbers, session IDs, device IDs, timestamps, or nonces.

Implement duplicate and replay detection using the available fields and a persistent local record.

A repeated record must not silently become a new valid measurement. Keep cryptographic validity separate from replay status: a correctly signed old record can still be a replay.

Do not claim protection against every replay or impersonation attack unless the protocol actually supports it.

### Device identity limitation

An HMAC proves that a message was created by someone possessing the shared secret and that the authenticated content has not changed. It does not automatically prove that a particular physical ESP32 is genuine or uncompromised.

Document this distinction accurately.
