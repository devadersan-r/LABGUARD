MASTER PROMPT — LABGUARD AUTHENTICATION AND EVIDENCE VERIFICATION SYSTEM
1. YOUR ROLE
Act as a senior cybersecurity engineer, Python developer, embedded systems engineer, cryptographic protocol designer, software architect and QA engineer.
Build a complete, functional project named LABGUARD.
The objective is to develop a low-cost, offline-first, independently verifiable integrity system for laboratory measurements captured by an ESP32 and a DS18B20 temperature sensor.
Do not build a mockup, a frontend-only simulation, or a system that merely displays hardcoded verification results. Implement the real cryptographic operations, evidence processing, key management, automated tests and hardware integration code.
Work incrementally. Inspect the current project directory before creating or modifying files. Preserve useful existing code. Do not overwrite existing work without inspecting it.
If hardware is not connected, implement and test the software using clearly labelled simulated evidence. Never claim that hardware integration has been tested unless it has actually been tested.
2. PROJECT OBJECTIVE
LABGUARD must demonstrate that unauthorized modifications to exported laboratory measurement records can be detected independently.
The intended workflow is:
	1	The DS18B20 measures temperature.
	2	The ESP32 creates a structured measurement record.
	3	The ESP32 authenticates the record using HMAC-SHA256 and a secret key.
	4	The authenticated record is transferred over USB Serial.
	5	The laptop saves records in a JSONL evidence file.
	6	The user opens LABGUARD and selects an evidence file.
	7	LABGUARD independently verifies the record authentication tags.
	8	The application reports the result and identifies failed records.
	9	The user can modify an exported measurement and repeat verification to demonstrate tamper detection.
The system must work locally without requiring an internet connection, cloud account, hosted database or external verification API.

5. DEFINE THE DATA FORMAT BEFORE IMPLEMENTING CRYPTOGRAPHY
First, document the exact schema and canonical byte representation.
Use an initial record schema similar to:
{ "schema": "labguard-v1", "session_id": "SESSION-001", "device_id": "DEVICE-01", "seq": 1, "elapsed_ms": 2000, "source": "DS18B20", "value": 28.50, "unit": "C", "auth": { "algorithm": "HMAC-SHA256", "key_id": "KEY-001", "tag": "64-character-lowercase-hexadecimal-tag" } }
This is a proposed schema. Finalize and document it before implementing the firmware and verifier.
Requirements:
	•	All required fields must have strict types and validation rules.
	•	Sequence numbers must be positive integers; reject booleans where an integer is expected.
	•	Measurement values must be finite numbers.
	•	Reject NaN, Infinity and -Infinity.
	•	Restrict identifiers and strings to documented lengths and permitted characters.
	•	Define whether extra fields are rejected or supported by a schema-versioning mechanism.
	•	Reject duplicate JSON object keys to prevent ambiguous interpretation.
	•	Do not silently coerce strings into numbers.
	•	Validate the algorithm and key identifier.
	•	Reject malformed or unsupported schemas clearly.
Use a deterministic canonical serialization specification that can be reproduced exactly in both Python and C++.
For the initial implementation, prefer a documented restricted JSON representation with:
	•	UTF-8 encoding.
	•	Fixed field names and field order.
	•	No insignificant whitespace.
	•	Explicit rules for string escaping.
	•	An exact numeric representation shared by both implementations.
	•	No ambiguous floating-point formatting.
Prefer storing temperature as an integer in hundredths of a degree Celsius, such as 2850 for 28.50 °C, internally and in the authenticated record schema. Name the field value_centi_c and document that the displayed temperature is derived by dividing by 100.
Use integers for the sequence number and elapsed milliseconds.
Define canonicalization over the complete record payload excluding the auth object. Document the precise bytes used for authentication.
Do not independently call Python json.dumps() and an arbitrary C++ JSON serializer and assume their outputs will match.
Add shared test vectors containing payloads, expected canonical bytes and expected HMAC tags. The same vectors must be usable to test Python and firmware implementations.
If the canonicalization contract cannot be implemented consistently, stop and explain the incompatibility rather than producing unreliable authentication.
6. CRYPTOGRAPHIC ENGINE
Implement actual HMAC-SHA256 using the Python standard library.
In labguard/crypto.py, provide functions similar to:
	•	compute_hmac(key, canonical_bytes)
	•	verify_hmac(key, canonical_bytes, supplied_tag)
	•	decode_key(encoded_key)
	•	encode_tag(tag_bytes)
Requirements:
	1	Use hmac.new(key, message, hashlib.sha256).digest() for generation.
	2	Encode tags as exactly 64 lowercase hexadecimal characters.
	3	Use hmac.compare_digest() for authentication-tag comparisons.
	4	Reject malformed tag encodings.
	5	Reject empty or incorrectly sized keys.
	6	Do not substitute ordinary SHA-256 for HMAC.
	7	Do not log the key or include it in exceptions.
	8	Include unit tests for correct tags, incorrect keys, altered messages, malformed tags and invalid key lengths.
	9	Use established cryptographic primitives rather than implementing SHA-256 or HMAC manually.
Document that HMAC provides symmetric-key authentication and integrity, not digital signatures or non-repudiation.
7. SECRET-KEY GENERATION AND MANAGEMENT
Build a key-management module that generates cryptographically random keys using Python's secrets module.
Requirements:
	•	Generate a fresh 32-byte random key.
	•	Represent keys using a documented encoding such as hexadecimal or Base64.
	•	Assign each key a non-secret identifier.
	•	Provide a CLI command for key generation.
	•	Never write keys to JSONL evidence files.
	•	Never embed real keys in source code or frontend assets.
	•	Never print a secret key during normal verification.
	•	Do not automatically generate a different key every time the verifier starts.
	•	Do not silently replace a key when a verification failure occurs.
	•	Handle missing keys and unknown key identifiers as explicit errors.
	•	Support multiple key identifiers if necessary.
	•	Separate the key used by a measurement-producing device from the interface and verification code.
For the development version, allow an operator to provide the key using an environment variable or a protected local key file outside the evidence directory.
On POSIX systems, create key files with restrictive permissions where supported. Explain that filesystem permissions do not provide hardware-backed protection.
Do not store real keys in a publicly accessible project folder or Git repository.
For the ESP32 prototype, clearly document the limitations of storing a software key in firmware or ordinary device flash. A key hardcoded into firmware can potentially be extracted.
Keep the key-generation and key-loading APIs separate so that a future secure element can be integrated without redesigning the entire verifier.
Never claim that the initial software-key arrangement offers production-grade key protection.

10. INDEPENDENT PYTHON VERIFIER
Implement labguard/verifier.py.
The verifier must treat imported evidence files as untrusted.
For every record:
	1	Parse one JSON object per line.
	2	Reject duplicate keys and malformed JSON.
	3	Validate the schema and types.
	4	Reconstruct the exact canonical payload bytes.
	5	Identify the key using the non-secret key identifier.
	6	Load the corresponding trusted key from the configured local key store.
	7	Recompute the HMAC-SHA256 tag.
	8	Compare the expected and supplied tags using hmac.compare_digest().
	9	Validate sequence and session consistency.
	10	Record the result for that specific line.
	11	Continue processing later records when safe, without concealing earlier errors.
Report at least:
	•	Overall result: VALID, INVALID or INCOMPLETE/UNVERIFIABLE.
	•	Evidence filename.
	•	Number of records encountered.
	•	Number of successfully authenticated records.
	•	Number of authentication failures.
	•	Number of malformed or structurally invalid records.
	•	Unknown-key and missing-key errors.
	•	Sequence gaps, duplicate sequences and ordering problems.
	•	Session consistency problems.
	•	First failing line number and failure category.
	•	Clear warnings when completeness cannot be established.
Use precise result semantics:
	•	VALID: all supplied records pass the implemented checks, with no detected inconsistency.
	•	INVALID: one or more records fail authentication or violate integrity-related validation rules.
	•	INCOMPLETE/UNVERIFIABLE: the file cannot be fully assessed because necessary information, such as a verification key or trusted completeness reference, is unavailable.
Document how the overall status is determined if several categories of errors occur.
Never report a file as VALID if any required record failed authentication or required validation.
Do not claim to identify exactly which field an attacker changed from an HMAC mismatch alone.
11. SEQUENCE VALIDATION AND HASH CHAINING
Implement basic sequence validation before attempting hash chaining.
Detect:
	•	Duplicate sequence numbers.
	•	Out-of-order records.
	•	Missing sequence numbers when the expected starting sequence and continuity rules are known.
	•	Unexpected session changes.
	•	Unexpected device or key identifiers where policy requires consistency.
Treat the following as a separate optional feature: HMAC-linked records or a hash chain.
Only implement chaining after the basic end-to-end HMAC system passes tests.
If chaining is implemented:
	•	Include the previous record's authentication tag or an explicitly defined previous-record digest in the authenticated payload.
	•	Define the first-record convention.
	•	Verify every link.
	•	Detect deletion, insertion, reordering and broken continuity where possible.
	•	Explain that a chain alone cannot prove that the final records have not been removed.
	•	Support a trusted external final checkpoint or manifest containing the expected record count and final tag if completeness verification is required.
Do not claim truncation detection unless a trusted completeness reference is actually checked.
