# LABGUARD Key Management & Hardening Guide

## 1. Overview
LABGUARD employs **HMAC-SHA256** (RFC 2104 / RFC 4231) symmetric message authentication to provide offline integrity and origin authentication for laboratory sensor records captured by an ESP32 microcontroller and DS18B20 temperature sensor.

Each measurement record generated by the sensor is authenticated using a secret symmetric key. When transferred to an analysis workstation, the verification engine independently reconstructs the canonical payload bytes and re-calculates the HMAC tag.

---

## 2. Key Specification
- **Primitive**: HMAC-SHA256 (256-bit message authentication code)
- **Key Length**: Exactly 32 bytes (256 bits)
- **Entropy Source**: Cryptographically Secure Pseudorandom Number Generator (`secrets.token_bytes(32)`)
- **Key Identifier**: Non-secret alphanumeric identifier (e.g., `KEY-001`) attached to record metadata (`auth.key_id`)
- **Supported Encodings**:
  - Lowercase Hexadecimal (64 characters)
  - Base64 (44 characters)
  - C++ Byte Array (`uint8_t[32]`) for microcontroller firmware

---

## 3. Hardened Key Storage & Permissions

### A. Python Verification Key Store (`keys/labguard_keys.json`)
- **Atomic Writes**: Uses temporary files and `os.replace` to ensure key store files are never partially written or corrupted on crash or power loss.
- **Fail-Safe Loading**: Malformed or corrupt key stores raise an explicit `KeyStoreCorruptedError` and are **never silently overwritten or replaced**.
- **POSIX Permissions**: Set strictly to `0600` (`-rw-------`, owner read/write only).
- **Git Ignore**: Protected by `.gitignore` against accidental commits.
- **Example Template**: `keys/keys.example.json` contains only an explicitly labelled dummy test key.

### B. Microcontroller Header (`firmware/LABGUARD_ESP32/secrets.h`)
- **Location**: `firmware/LABGUARD_ESP32/secrets.h`
- **Format**: `static const uint8_t LABGUARD_SECRET_KEY[32] = { ... };`
- **Atomic Writes & Permissions**: Written atomically with `0600` permissions.
- **Git Ignore**: Protected by `.gitignore`. Example template at `firmware/LABGUARD_ESP32/secrets.h.example`.

### C. Fail-Closed Key Resolution (No Unsafe Generic Fallback)
In accordance with Section 3 of `correction.txt`:
- Generic fallback environment variables (`LABGUARD_SECRET_KEY`) have been **permanently removed**.
- Key resolution requires either:
  1. An entry in `keys/labguard_keys.json` matching `auth.key_id`.
  2. An explicit key-specific environment variable matching `LABGUARD_KEY_<KEY_ID>` (e.g., `LABGUARD_KEY_KEY_001`).
- Requests for unknown key IDs **fail closed immediately** (`KeyNotFoundError`). An unknown key ID can never authenticate using an unrelated secret.

## 4. CLI Provisioning & Safe Rotation

### Provision a Fresh Key
```bash
python3 scripts/generate_key.py --key-id KEY-001
```

### Rotate an Existing Key
When an existing key is compromised or scheduled for rotation, use the `--rotate` flag:
```bash
python3 scripts/generate_key.py --key-id KEY-001 --rotate
```

### Rotation Safeguards
- Synchronously updates both `keys/labguard_keys.json` and `firmware/LABGUARD_ESP32/secrets.h`.
- Passing `--no-esp32` during rotation is blocked unless `--confirm-no-esp32` is explicitly passed, preventing unnoticed desynchronization between sensor node and verifier.
- **Zero Secret Leakage**: The CLI tool **never prints secret values** (hex, base64, or export commands) in terminal output or logs. Only non-sensitive metadata (key ID, algorithm, file paths, permissions) is reported.

---

## 5. Threat Model & Limitations

> [!WARNING]
> **Flash Memory Extraction**:
> Storing software keys in microcontroller flash memory is intended for prototypes and lab demonstrations. A key in flash can potentially be extracted via physical probing, JTAG interfaces, or flash dump utilities. For high-security environments, combine ESP32 Flash Encryption + Secure Boot, or integrate an external hardware secure element (e.g., Microchip ATECC608A / OPTIGA Trust M).

> [!NOTE]
> **Symmetric HMAC vs Digital Signatures**:
> HMAC provides **data integrity** and **origin authentication** between parties sharing the secret key. Because both the generator (ESP32) and verifier (laptop) hold the symmetric key, HMAC does *not* provide non-repudiation or third-party cryptographic proof against someone who possesses the verification key.

> [!IMPORTANT]
> **Zero Key Leakage Rule**:
> Secret keys are **never** logged, never included in exception messages, never exported in JSONL evidence records, and never transmitted in UI responses.
